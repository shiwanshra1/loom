# Forge Loom — Firebase Migration Todo Tickets

Ticket breakdown for executing `docs/superpowers/specs/2026-08-29-firebase-migration-design.md`'s 7-phase plan, using the concrete schema decisions in `docs/firestore-database-design.md`. Grounded in the actual current codebase (`apps/server/src/**`, `apps/client/src/**`) as of 2026-09-01 — every ticket names the real file(s) it touches, not a hypothetical structure.

**Conventions:** IDs are `FB-<phase>.<n>`. Each phase closes with the same verification rigor every prior milestone-1.md phase used (typecheck/lint/build across all 3 workspaces + a live end-to-end exercise, per `memory.txt`'s established pattern) — restated once at the top rather than repeated on every ticket. Checkpoint and commit locally after each phase; push to `origin/main` only on explicit request (same cadence as every phase to date).

## Phase 2 — Auth cutover

- [ ] **FB-2.1 — Rewrite `apps/server/src/middleware/authenticate.ts`.** Replace JWT-verify + Redis-lookup with `admin.auth().verifyIdToken(bearerToken)`. `req.user` population changes shape (Firebase decoded token has `uid`, not a Mongo `_id`); every downstream consumer of `req.user._id`/`req.user.id` across all 22 controllers needs to switch to `req.user.uid` — audit this specifically, don't assume it's confined to the middleware file.
- [ ] **FB-2.2 — Delete refresh-token plumbing.** Remove `/auth/refresh` and any logout-time token-revocation logic from `apps/server/src/modules/auth/` — Firebase Auth's client SDK handles token refresh transparently; the server never issues or rotates its own refresh tokens again. Remove `refreshTokenVersion` from the `users` write path (already dropped from the schema per the design doc).
- [ ] **FB-2.3 — Rewrite registration.** `POST /auth/register` (`apps/server/src/modules/auth/`) now calls `admin.auth().createUser({email, password, uid: <deterministic>})` (see design doc §7 — decide and lock in the `uid` strategy **here**, before any real accounts exist in the Firebase project, since retrofitting it later is much harder) instead of writing a `passwordHash`. Still creates the role-specific profile document afterward — same two-step shape as today (`User` + profile), just against Firestore instead of Mongoose. `collegeProvisioning.ts`'s founding-a-college-on-register logic (Phase 6 of milestone-1.md) needs its Mongo calls swapped to Firestore repository calls but its business logic is unchanged.
- [ ] **FB-2.4 — Rewrite login/logout/`me`.** Server-side login no longer issues its own tokens — the client's Firebase SDK does `signInWithEmailAndPassword` directly against Firebase Auth, and the server's job shrinks to "does this ID token verify, and here's the app-specific profile data for it" via `GET /me`. Decide whether `POST /auth/login` stays as a thin server endpoint at all (it may become entirely client-side, with the server only ever seeing already-authenticated requests) — document the decision here, since it changes the API surface, not just its implementation.
- [ ] **FB-2.5 — Rewrite `AuthContext.tsx`.** `apps/client/src/auth/AuthContext.tsx` rebuilt around `onAuthStateChanged`/`signInWithEmailAndPassword`/`signOut`/`getIdToken()`, replacing the current in-memory-access-token + httpOnly-refresh-cookie bootstrap-via-silent-refresh flow.
- [ ] **FB-2.6 — Rewrite `apiClient.ts`'s request wrapper.** `apps/client/src/lib/apiClient.ts` attaches `await currentUser.getIdToken()` as a Bearer header instead of managing its own 401-retry-after-refresh interceptor (the Firebase SDK auto-refreshes client-side, so that interceptor logic is deleted, not adapted).
- [ ] **FB-2.7 — `users/{uid}` Firestore repository.** New repository module exposing the same-shaped functions the auth service already calls (`findById`, `updateStatus`, etc. — see design doc §2.1) so downstream modules' calls don't need to change shape, only their import.
- [ ] **FB-2.8 — Verify end-to-end against the emulator.** Register (each of the 11 self-registerable roles + a manually-provisioned `course_admin`/`forge_admin`), login, `GET /me`, logout, suspended-account-blocks-login, wrong-password-rejected — same test matrix Phase 1 of milestone-1.md originally proved for the JWT system, now against Firebase Auth + the emulator.

## Phase 3 — Core data migration (Users/Profiles, Colleges/Cohorts/Teams, Courses/Enrollments/Sessions/Attendance/VideoProgress)

- [ ] **FB-3.1 — Firestore repository layer, one module per collection.** For each of: `studentProfiles`, `mentorProfiles`, `trainerProfiles`, `speakerProfiles`, `hrProfiles`, `sponsorProfiles`, `collegeProfiles`, `communityLeaderProfiles`, `mediaPartnerProfiles`, `memberProfiles`, `courseAdminProfiles`, `colleges`, `cohorts`, `teams`, `courses`, `courseSessions`, `enrollments`, `attendanceRecords`, `videoProgress`, `assessments` — build a thin repository exposing the same functions the existing service layer calls today (per the migration design doc's own stated approach: minimal rework above the persistence call sites). Use the deterministic-ID schemes from the design doc §2 wherever a Mongo compound-unique index existed (`courseSessions/{courseId}_{dayNumber}`, `attendanceRecords/{sessionId}_{studentId}`, `videoProgress/{studentId}_{courseId}_{dayNumber}`, and every profile keyed on `{uid}`).
- [ ] **FB-3.2 — Swap `modules/courses/`, `modules/enrollments/`, `modules/sessions/`, `modules/videoProgress/`, `modules/colleges/`, `modules/cohorts/`, `modules/teams/` service files onto the new repositories.** Business logic (status transitions, `courseAccess.ts`'s shared ownership checks, session-materialization-on-enrollment, the 90%-watched completion threshold) is unchanged — only persistence calls change.
- [ ] **FB-3.3 — `communityLeaderProfiles.members[]` subcollection conversion.** Per design doc §2.1, this is a genuine schema change, not a mechanical port — implement `communityLeaderProfiles/{uid}/members/{memberUid}` as a subcollection and update `modules/communityMembers/` accordingly. (Community/Events modules broadly land in Phase 5 below, but this specific structural decision belongs with the rest of the profile-collection work since it's the same collection family.)
- [ ] **FB-3.4 — `courseAccess.ts` review.** The shared "can this viewer see/manage this course" helper (used by sessions/assessments/progress rollup) currently does Mongoose lookups directly — confirm it's rewritten against the new repositories rather than left calling dead Mongoose code paths.
- [ ] **FB-3.5 — Verify end-to-end against the emulator.** Re-run the exact live-flow test matrix Phase 6 of milestone-1.md originally used: register with a college picker, confirm college-founding-on-register, create/publish a course with an assigned trainer, enroll a student (confirm session materialization for offline courses), mark attendance, post video progress and confirm the 90% completion threshold, pull the KPI/course-progress rollup.

## Phase 4 — Citadel + Score Engine + Certifications + Bookings + Notifications

- [ ] **FB-4.1 — Firestore repositories for Citadel collections.** `problemStatements`, `sprints` (deterministic ID `{teamId}_{cycleNumber}`), `milestoneSubmissions`, `investorAccessGrants` (deterministic ID `= teamId`), `bookmarks`/`interestExpressions` (deterministic ID `{userId}_{problemStatementId}`).
- [ ] **FB-4.2 — Port the Citadel state machine.** `modules/sprints/sprint.service.ts`'s submit→feedback→complete transitions, sprint-cycle materialization on `PATCH /teams/:id`, and the investor-unlock check — same business rules, new persistence.
- [ ] **FB-4.3 — Port the BullMQ Citadel worker.** `jobs/citadelQueue.ts`/`jobs/citadelWorker.ts` stay on BullMQ+Redis unchanged per the locked-in decision (Redis's role narrows to pure job-queue duty) — only the worker's own Firestore reads/writes (checking all-3-sprints-complete, creating `investorAccessGrants`) change.
- [ ] **FB-4.4 — `scoreEvents` repository + score worker port.** `jobs/scoreQueue.ts`/`jobs/scoreWorker.ts` and `modules/scoring/scoreEvent.service.ts` — same formula (`0.2×events + 0.4×project + 0.3×mentor + 0.1×team`), same category-cap/average-not-sum rules, new Firestore reads. This module has no HTTP route (per the repo audit) — don't accidentally add one that wasn't there before.
- [ ] **FB-4.5 — Certificates: PDF/QR generation stays, storage swaps.** `pdfkit`/`qrcode` generation logic in `modules/certificates/` is unchanged; only the upload/presign step moves from `@aws-sdk/client-s3`+`@aws-sdk/s3-request-presigner` to `firebase-admin`'s Storage module, writing to `certificates/{studentId}/{enrollmentId}.pdf` per the design doc's path convention. `certificates/{enrollmentId}` becomes the Firestore doc ID (replacing the Mongo unique index on `enrollmentId`). The public `token`-based verify lookup (`GET /certificates/verify/:token`) needs a `where('token', '==', token)` query — confirm `express-rate-limit`'s 20 req/min guard is still wired on this route.
- [ ] **FB-4.6 — Bookings: the `$or`-query split.** Per design doc §2.5, Firestore has no single-query equivalent of Mongo's `$or` across `requesterId`/`mentorId`. Rewrite `modules/bookings/`'s `listMyBookings` as two queries (one per field, each using its own composite index from the design doc §5) merged and sorted in the service layer. This is a genuine logic change, not just a repository swap — call it out in code review.
- [ ] **FB-4.7 — Notifications repository + trigger wiring.** `modules/notifications/` plus every trigger site that fires one today (booking created/cancelled, sprint reviewed, investor access granted, session cancelled, certificate issued) — confirm every trigger call site is found and ported; this list is easy to under-migrate since triggers are scattered across multiple modules' service files rather than centralized.
- [ ] **FB-4.8 — Verify end-to-end against the emulator.** Re-run Phase 7/8-of-milestone-1.md's original live test matrix: full problem-statement→team-assignment→3-sprint-cycle→investor-unlock flow (confirm the worker actually ran, not just that enqueue didn't throw); a fresh sprint's builderScore computation matching the known hand-calculated value (43, per `memory.txt`'s Phase 8 entry) as a regression check that the formula ported correctly; certificate issuance + real PDF download + public verify; booking in both directions with correct-party notification.

## Phase 6 — Admin analytics + automated tests

- [ ] **FB-6.1 — Port `modules/admin/` aggregate queries.** `GET /admin/national-stats`'s pure counts (`totalColleges`, `totalStudents`, `venturesLaunched`) move to Firestore `count()` aggregation queries. `GET /admin/analytics`'s builderScore distribution and 7-day attendance trend have no aggregation-pipeline equivalent (design doc §6) — implement as an in-code bucketing pass over the read documents, and add a code comment flagging this as a disclosed cost/latency difference from the Mongo original, worth revisiting if usage grows past the original 5k–50k target.
- [ ] **FB-6.2 — `GET /admin/users` + `PATCH /admin/users/:id/status`.** Port the suspend/reinstate flow onto the `users` Firestore repository; confirm `authenticate.ts`'s status check (`status === 'suspended'` blocks login) still works against the new repository.
- [ ] **FB-6.3 — Repoint the test suite at the emulator.** The existing `vitest`+`supertest` suite (20 tests across 5 files, `apps/server/src/__tests__/`) currently runs against a real local Mongo `forgeloom_test` database with a `globalSetup` that refuses to run unless `MONGO_URI` contains `forgeloom_test` (a deliberate guardrail against ever hitting real dev data). Rewrite this guardrail for the Firestore emulator equivalent — e.g. requiring `FIRESTORE_EMULATOR_HOST` to be set and refusing to run otherwise — so the "never touches real data" guarantee survives the migration. Re-verify all 5 test files' scenarios (auth, enrollment+payment, attendance, Citadel investor-unlock job, score-recompute job) pass against the emulator; the investor-unlock/score-recompute tests specifically call the worker files' exported business-logic functions directly (`checkInvestorUnlock`, `recomputeBuilderScore`) rather than round-tripping through BullMQ — confirm that pattern still holds after the persistence swap.
- [ ] **FB-6.4 — Verify.** Full suite green against the emulator, run multiple consecutive times (the existing suite needed a `pool:'forks', singleFork: true` fix for a flaky teardown race under Mongo — check whether an equivalent stability issue exists under the emulator and fix if so, rather than assuming it doesn't).

## Phase 7 — One-time data migration, cutover, cleanup

- [ ] **FB-7.1 — Write the Mongo → Firestore migration script.** One-time, run once against real (non-emulator) Firestore once FB-0.1's service account key is available. Must implement the `uid: mongoUser._id.toString()` strategy from design doc §7 for every `createUser()` call — **do this first, before migrating any other collection**, since every other collection's foreign keys depend on user IDs being preserved identically. Migrate in dependency order: users → profiles → colleges/cohorts/teams → courses/enrollments/sessions/attendance/videoProgress → citadel collections → scoreEvents → certificates/bookings/notifications → community/events/talentpool-adjacent collections. Explicitly skip `placements` (zero existing data, per design doc §2.7).
- [ ] **FB-7.2 — Fan out `CommunityLeaderProfile.members[]` into the new subcollection** as part of the same script (per FB-3.3's structural decision) — this is a one-to-many expansion, not a 1:1 document copy, so it needs its own migration logic distinct from every other collection's straightforward copy.
- [ ] **FB-7.3 — Cutover.** Point `apps/server` at real Firestore/Auth/Storage (remove emulator env vars from the production/staging config path). Confirm every seeded dev account (`student1@forgeloom.dev` etc.) still logs in post-cutover.
- [ ] **FB-7.4 — Cleanup.** Remove `mongoose` and any Mongo-specific dependencies from `apps/server/package.json`; remove the `mongo` service from `infra/docker-compose.yml`; remove MinIO (`@aws-sdk/*` deps, `config/s3.ts`, the `minio` docker-compose service) now that Firebase Storage fully replaced it; update `docs/forge-loom-architecture.md` and `docs/forge-loom-local-to-cloud-migration.md` to reflect the new Firebase-based architecture (both currently describe the pre-migration Mongo/Redis/MinIO/Atlas stack and will be actively misleading to a future reader once this phase ships).
- [ ] **FB-7.5 — Final verification.** Full typecheck/lint/build/test suite green against real (non-emulator) Firestore; live end-to-end smoke test of one flow per major domain area (auth, course enrollment+payment, attendance, Citadel sprint cycle, certificate issuance, booking, notification) against the real Firebase project — the same level of rigor `memory.txt` records for every one of the original 10 milestone-1.md phases.
