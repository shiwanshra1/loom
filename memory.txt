## Earlier context (2026-08-09 through 2026-08-29, compacted 2026-09-07)

Forge Loom is Winnovation's FORGE program platform: a multi-role LMS/execution platform (11+ roles: Student/Mentor/Trainer/Speaker/HR/Sponsor/CollegeAdmin/CommunityLeader/MediaPartner/Member/ForgeAdmin, plus CourseAdmin added later), originally spec'd as MERN (MongoDB+Express+React+Node), target 5k-50k users. Built in Claude Code across two roadmaps:

1. **Initial architecture + Phase 1 build** (2026-08-09): `docs/forge-loom-architecture.md`/`forge-loom-wireframes.md`/`forge-loom-local-to-cloud-migration.md`/`forge-loom-screen-to-data-binding.md` written; npm-workspaces monorepo scaffolded (`packages/shared-types`, `apps/server` Express+Mongoose, `apps/client` Vite+React); JWT+Redis auth for all 11 roles; Docker Desktop/WSL2 installed (had some friction, resolved); full frontend built phase-by-phase (Shell+Auth, Student dashboard matching a provided render.pdf, Mentor dashboard, remaining 9 roles on mock data); pushed to `https://github.com/shiwanshra1/loom` on `main`.
2. **`docs/milestone-1.md` — 10-phase roadmap** (2026-08-28/29), executed phase by phase, each with real backend + verified live end-to-end (not just typechecked): Phase 1 Course Admin role + course/syllabus; Phase 2 Course Catalog/Enrollment + real Razorpay payments (test-mode key provided by user then, since lost from context — see Phase 0 of the Postgres migration below); Phase 3&4 Attendance/Sessions + YouTube video progress (built together); Phase 5&6 Progress/KPI dashboards + Colleges/Cohorts/Teams (built together; this is where `collegeId` scoping and the two-college-cluster seed data — college1/college2 — were introduced); Phase 7 Citadel (sprints/problem statements/investor-unlock automation via BullMQ); Phase 8 Score Engine/Certifications(PDF+QR+S3)/Bookings/Notifications; Phase 9 Talent Pool + the other 6 roles' real backends; Phase 10 Admin analytics, `Placement` schema-stub, `vitest`+`supertest` test suite (5 files: auth/enrollment/attendance/citadel/score), and a cloud-migration section that was explicitly left undone (blocked on real MongoDB Atlas/Redis/S3 credentials the user never provided — this blocker became moot once the direction changed to Postgres, see below).

All 10 phases shipped and were the live, working app as of 2026-08-29. Established conventions that still hold: checkpoint + commit locally after each phase, push to `origin/main` only on explicit request; disclose every judgment call made without asking; verify live over HTTP against the real Docker stack, not just typecheck/build.

## 2026-09-01 (Firebase migration drafted, then cancelled same week; PostgreSQL/Prisma chosen instead)

**Firebase drafted, never implemented:** A MongoDB→Firebase/Firestore migration was designed (`docs/superpowers/specs/2026-08-29-firebase-migration-design.md` committed; a Firestore schema doc + ticket breakdown drafted uncommitted) but **zero code was ever written against it**.
**Reversed same session:** user said "migrate db to prisma postgres, drop firebase entirely, use PERN... drop mongodb as well." This is a much narrower change than Firebase would have been — only the persistence layer moves; Express/JWT+Redis auth/BullMQ/MinIO+S3 all stay exactly as-is (verified independent of `MONGO_URI` in `env.ts`).
**Delivered:** Archived the 3 Firebase docs to `docs/archive/` with a superseded banner (not deleted). Created `docs/postgres-database-design.md` (full Prisma schema for all 34+ Mongo collections → 44 Prisma models/tables, Mermaid ER diagram, `onDelete`/`onUpdate` policy) and `docs/prisma-migration-tickets.md` (10-phase ticket breakdown, T0-T9 + cross-cutting). Updated `docs/forge-loom-architecture.md` and `docs/forge-loom-local-to-cloud-migration.md` to describe Postgres/Prisma instead of Mongo/Atlas throughout.
**Key design decisions** (all in the docs): `String @id @default(cuid())` PKs everywhere (not `uuid`/autoincrement) specifically so the final Phase 8 data migration can reuse literal old Mongo `_id` values with zero remapping table. Money fields (`Course.price`, `Enrollment.paymentAmount`) → `Decimal`. Three-way array taxonomy: scalar lists → Postgres arrays, FK-reference arrays → join tables or dropped-if-provably-derivable (verified via grep against real service code, not assumed), embedded sub-documents → normalized child tables with an added `order` column where Mongo's array position was implicit.
**2026-09-07 follow-up — frontend tickets gap found:** User asked whether frontend tickets existed; none did. Investigated the real client code rather than assuming "zero frontend changes" held: confirmed Talent Pool's cursor is genuinely opaque client-side (safe), but found `course.price` is typed as a plain `number` in 3 client files with no defense against Prisma's `Decimal` not auto-serializing to a JSON number. Added **Phase 10 — Frontend regression verification** to the tickets doc (3 verification-only tickets, no client code changes expected or made).
**Pushed to `origin/main`** later that session (2 commits: the original committed Firebase spec doc + the full Postgres pivot).

## 2026-09-07 — Executing the Prisma migration (Phases 0-3 done so far, live and verified each time)

**Established execution pattern, repeated every phase:** read the ticket doc section first, but verify every assumption in it against the real current code (ticket-writing happened before any code was touched, so some assumptions don't survive contact — always disclosed and corrected in the ticket doc + here, never silently patched over). Do NOT delete old Mongoose model files as tickets originally said — other not-yet-migrated modules still import them; actual deletion is deferred to Phase 9, once nothing references them. Verify with typecheck/build/lint + the automated suite + a live HTTP smoke test against a real running dev server every single phase — an automated-tests-only pass has repeatedly missed real issues in this migration that live HTTP testing caught. Commit locally after each phase; push only on request.

**Pre-flight (before Phase 0):** `apps/server/.env.local`/`.env.test` didn't exist in this checkout at all (only `.env.example`) — created both fresh with dev-only placeholder secrets (JWT/S3 following established convention; Razorpay is an explicit placeholder since real test-mode keys aren't available in this session's context anymore — payment flows are non-functional until real keys are supplied again, disclosed and confirmed working-as-expected via a graceful 502, not a crash, in Phase 2's live test). Found an unrelated project's own Postgres container already bound to host port 5432 (`lms-db-1`) — used port **5433** for this project's Postgres throughout.

**Architectural landmine found and escalated before writing any Phase 1 code:** Prisma's `cuid()` PKs aren't valid Mongo ObjectId hex, and every Mongoose FK field (`Team.trainerId`, `Enrollment.studentId`, `Notification.userId`, `ScoreEvent.studentId`, etc.) strictly casts to ObjectId. A live phase-by-phase cutover means a Postgres-native account can throw a Mongoose CastError the instant a still-Mongo module tries to reference it. Presented 3 options via AskUserQuestion; **user chose "accept the gap, it's dev-stage"** — proceed live, let not-yet-migrated features be temporarily unreachable for new accounts until their own phase lands or Phase 8 (final data migration) runs. This decision has since paid off exactly as scoped — the same guard pattern (`mongoose.isValidObjectId(id)` check, silently skip rather than throw) has been reapplied cleanly in `notification.service.ts` (Phase 2), `scoreEvent.service.ts` (Phase 3), and implicitly in `college.service.ts`'s Mongo-Team-count fallback (Phase 1).

**Phase 0 (infra) — done:** `infra/docker-compose.yml` gained `postgres` **alongside** Mongo (not replacing it — correction to the ticket's "replace" wording; Mongo still serves every unmigrated module through Phase 8), plus `infra/postgres-init/01-create-test-db.sql` auto-creating `forgeloom_test`. Full 44-model `apps/server/prisma/schema.prisma` (byte-extracted from the design doc via `awk`, no transcription drift). New `apps/server/src/config/prisma.ts` (client singleton, wired into `server.ts` alongside — not instead of — `connectDb()`). `env.ts` gained `databaseUrl`, **kept** `mongoUri` (another correction). `prisma migrate dev --name init` applied cleanly to both `forgeloom_dev`/`forgeloom_test` (44 tables each).

**Phase 1 (Identity: auth/colleges/communityMembers/hrProfile/talentPool) — done:** Full Prisma cutover of `auth.*`, `profileFactory.ts`, `collegeProvisioning.ts`, `college.*`, `communityMember.*`, `hrProfile.*`, `talentPool.*`. `talentPool.service.ts`'s free-text search (substring match across a `String[]` column, no Prisma query-builder equivalent) uses a fully parameterized `$queryRaw`/`Prisma.sql` to preserve exact original behavior. `scripts/seed.ts` fully rewritten to Prisma too (unticketed but required — it calls the now-Prisma-only `profileFactory`/`collegeProvisioning` directly). New `apps/server/src/utils/prismaEnum.ts` (thin `toPrismaEnum`/`fromPrismaEnum` cast helpers for the "Prisma enum vs shared-types enum, same values, nominally incompatible" gap — used from Phase 2 onward, Phase 1's own inline casts weren't retrofitted). `attendance.test.ts`/`enrollment.test.ts` had to be `describe.skip`-ed (disclosed) — they create a Mongo-only test user then log in over now-Postgres-only HTTP, an irreconcilable requirement until Phase 2.

**Phase 2 (Courses/Enrollment/Sessions/VideoProgress/Assessments/Certificates) — done:** Full Prisma cutover of all 8 files/modules. Un-skipped `attendance.test.ts`/`enrollment.test.ts` by rewriting them onto a new `createTestUserPg` helper (Prisma-backed, added alongside the existing Mongo-backed `createTestUser` which stays for Phase 3/4's still-Mongo test suites).
