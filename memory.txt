# Forge Loom — Project Memory Log
# Manual continuity log — read this first, then check docs/ for full deliverables.

## Earlier context (2026-08-09 through 2026-09-08, compacted 2026-09-09)

Forge Loom is Winnovation's FORGE program platform: a multi-role LMS/execution platform (12 roles: Student/Mentor/Trainer/Speaker/HR/Sponsor/CollegeAdmin/CommunityLeader/MediaPartner/Member/ForgeAdmin/CourseAdmin), built in Claude Code across three roadmaps, all fully shipped:

1. **Initial architecture + Phase 1 build** (2026-08-09): monorepo scaffolded (`packages/shared-types`, `apps/server` Express, `apps/client` Vite+React); full frontend for all 11 original roles; pushed to `https://github.com/shiwanshra1/loom` on `main`.
2. **`docs/milestone-1.md` — 10-phase MERN roadmap** (2026-08-28/29): real backends for every role on MongoDB — courses/enrollment/Razorpay, attendance/video progress, Citadel (sprints/problem statements/investor unlock via BullMQ), score engine/certificates/bookings/notifications, talent pool, admin analytics. All verified live, not just typechecked.
3. **Postgres/Prisma migration, 10 phases** (2026-09-01 through 09-07, `docs/prisma-migration-tickets.md`): a Firebase migration was drafted then cancelled same week in favor of "PERN, drop Mongo entirely." Full schema redesign (`cuid()` PKs everywhere so old Mongo `_id` values could be reused with zero remapping), then a phase-by-phase live cutover of every module (Identity → Courses → Citadel → Scoring → Engagement → Admin), a test-harness rewrite, a one-time historical-data migration script (written and verified against a scratch DB, deliberately never run against real dev data per user's choice — old Mongo data and live-tested Postgres data shared emails but not ids), full Mongo/Mongoose retirement, and frontend regression verification. All 10 phases shipped, live-verified, pushed to `origin/main`. One open external dependency remains: Razorpay test-mode keys are placeholders (payment flows 502 gracefully, not crash) since real ones were never supplied in this session's context. Full phase-by-phase detail, if ever needed again, is only in `git log`/old commit messages now.

**Established conventions that carried forward into the current initiative**: checkpoint + commit locally after each phase, push to `origin/main` only on explicit request; disclose every judgment call and every ticket-assumption correction, never silently patch over one; verify live over HTTP against the real Docker stack every phase, not just typecheck/build — this has repeatedly caught real issues automated tests alone missed.

## 2026-09-08/09 — New initiative: Forge Admin hierarchy, college onboarding & bulk roster management — ALL 9 PHASES DONE

**Why**: replace "anyone self-registers, a self-registering College Admin instantly founds a brand-new college with zero approval" with a top-down FORGE-operated model — a Forge Admin creates peer Forge Admins and onboards colleges (College + College Admin account together); that College Admin then runs their own college end-to-end (batches, college-scoped courses, mentor/trainer invites, CSV bulk student upload with auto-generated passwords + one-click welcome emails). Admin-provisioned accounts are forced to change their password on first login. Full plan + ticket breakdown: `docs/forge-admin-hierarchy-tickets.md` (mirrors the Prisma migration tickets doc's discipline — checkboxes, disclosure notes, nothing marked done until verified live).

**Locked decisions** (confirmed via AskUserQuestion before any code was written): (1) the "per-college Forge Admin" is the existing `CollegeAdmin` role reused as-is, not a new role; (2) College Admin CAN create courses scoped to their own college (real schema change); (3) self-registration removed for the 4 college-scoped roles only (Student/Mentor/Trainer/CollegeAdmin) — the other 6 roles keep self-registering untouched; (4) stays at the org/roster layer, no deeper Citadel-ops build from the reference rulebook PDFs.

**Phase 1 (schema + infra)**: `User.mustChangePassword`, `StudentProfile.cohortId`/`rollNumber` (Batch = existing `Cohort` model reused), `Course.collegeId` (unused until later phases) — all additive. New `generatePassword.ts`, `config/mail.ts` (nodemailer), `welcomeEmailQueue.ts`/`welcomeEmailWorker.ts` (BullMQ, mirrors the existing score-recompute pattern). Found: `MentorProfile`/`TrainerProfile` have no display-name field at all, so the welcome-email payload carries `email`/`displayName` directly. Two environment quirks fixed (unrelated to the feature): non-interactive `prisma migrate dev` workaround (`migrate diff` + hand-created migration + `migrate deploy`), and this shell's `localhost` DNS hang (local env files now use `127.0.0.1`).

**Phase 2 (password-change)**: `POST /auth/change-password`, `PublicUser.mustChangePassword` threaded through, forced-change UI. First real usage of bumping `refreshTokenVersion` (previously stored/compared, never incremented).

**Phase 3 (⚠ `Course.createdBy` repoint)**: 3-step migration moved it from `CourseAdminProfile.id` to `User.id` directly (needed so College Admins, who have no `CourseAdminProfile` row, can create courses). Caught and correctly recovered from a stale-test-data migration failure rather than forcing it through.

**Phase 4 (Forge Admin + College onboarding)**: `modules/admin/accountProvisioning.service.ts` (`createAdminManagedAccount`) is the one funnel for every admin-driven account from here on. `POST /colleges` repurposed into a transactional onboarding call. New `GET /admin/colleges`, `POST`/`GET /admin/forge-admins`. **Judgment call**: both onboarding endpoints return the plaintext temp password once in the response (shown once in a UI modal) since the welcome email is only best-effort queued.

**Phase 5 (⚠ remove self-registration for 4 roles)**: Narrowed `SELF_REGISTERABLE_ROLES` itself (shared-types) rather than adding a parallel check. Folded college-founding logic into one `createCollegeWithAdmin` function (`college.service.ts`), used by both onboarding and `seed.ts`. Deleted the now-fully-dead `collegeProvisioning.ts`.

**Phase 6 (College Admin roster + batches)**: New `modules/college/roster.*` — single-add students/mentors/trainers, `PATCH .../batch`. Widened `POST /cohorts` to also allow College Admin. New `components/ui/DataTable.tsx` primitive; `pages/college/{Batches,Students,Faculty}Page.tsx`.

**Phase 7 (CSV bulk upload + welcome emails)**: `POST /college/students/bulk` — sequential row processing (needed for in-batch dedup), each row's User+StudentProfile creation is one `$transaction`, returns per-row `created`/`error` results with **HTTP 207**. Welcome emails are a deliberate separate step (`.../bulk/send-welcome-emails`), not automatic — takes `{userId,email,displayName,tempPassword}` straight from the bulk-create response since passwords are never stored in plaintext. New `FileDropInput.tsx` + `parseCsv.ts` (papaparse, new dependency). **Disclosed perf finding**: 200-row load test took ~107s (~0.5s/row), traced to `bcryptjs`'s cost-12 hashing being CPU-bound on Node's single thread — pre-existing, app-wide behavior, not something this phase introduced; a 500-row upload would take several minutes synchronously, acceptable for what was ticketed but flagged as a future background-job candidate.

**Phase 8 (College Admin course creation)**: Widened `POST/PATCH /courses(/status)` and `GET /courses/mine` to accept CollegeAdmin (collegeId forced from session; CourseAdmin variant unchanged, stays global). Catalog visibility: a college-scoped course is only visible to its own college + Forge Admin, even published — a shared `catalogVisibilityFilter()` backs `GET /courses`/`GET /catalog`. **Extended past the ticket's literal wording, disclosed**: also gated `getCourseById` and `enrollment.service.ts`'s `createEnrollment` (both now 404 for an outside viewer) — without those, "invisible in the catalog" wouldn't actually mean "can't view or enroll via a direct/guessed link." Frontend reuses `course-admin`'s exact list/editor components via a new optional `basePath` prop rather than duplicating ~330 lines of form logic.

**Phase 9 (Forge Admin cross-college drill-in)**: New `resolveViewedCollegeId`/`requireViewedCollegeId` helpers (`middleware/scopeToCollege.ts`) — Forge Admin supplies `?collegeId=` explicitly (their own `collegeId` is always null); every other role's query-string value is ignored, always forced to their own session (live-verified a College Admin cannot escape their own scope this way). Applied only to **read** endpoints (roster list, faculty, programs, courses/mine) — every write endpoint stays College-Admin-only, matching "view, not edit." New `pages/admin/CollegeDrillInPage.tsx` reuses College Admin's own data hooks parameterized by collegeId. T9.3 (optional Trainer/Events polish) explicitly skipped as genuine scope-creep, per its own ticket wording.

**Verification discipline held for all 9 phases**: typecheck/build/lint clean across all 3 workspaces every time, `npx vitest run` green twice consecutively every time (20/20 throughout — no test file needed changes past Phase 3), live HTTP smoke test against the real dev stack every phase (all test/load-test data cleaned up afterward each time). Full disclosure detail for every phase, including every judgment call and every place a ticket's literal wording was extended or corrected, lives in `docs/forge-admin-hierarchy-tickets.md`.

**Git state**: all 9 phases committed individually on `feature/forge-admin-hierarchy` (commits `d12b48f` through the Phase 9 commit). Only Phase 1 has been pushed to `origin` so far — the rest are local-only pending an explicit push request.

**Test credentials still live in the dev DB** (all seed accounts use `test1234` unless noted): the two Phase 1 injections `student3@forgeloom.dev` (password now `newpass123`, not the original — changed during Phase 2's live test, `mustChangePassword: false`) and `mentor3@forgeloom.dev` / `60282532` (`mustChangePassword: true`, untouched since Phase 1).
